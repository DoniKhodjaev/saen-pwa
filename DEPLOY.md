# Публикация Saen и настройки Vercel

Изменения подготовлены в PR #1. Vercel автоматически создал защищённый Preview deployment; его сборка успешна. Слияние PR и production deploy не выполнялись.
Наличие домена, активного deployment, Redis и рабочих Telegram credentials необходимо проверить в аккаунтах владельца.

## Настройки проекта

| Поле Vercel | Значение |
| --- | --- |
| Git repository | `DoniKhodjaev/saen-pwa` |
| Production Branch | `main` |
| Framework Preset | Other |
| Root Directory | корень репозитория |
| Node.js Version | 24.x |
| Install Command | `npm ci` |
| Build Command | `npm run check` |
| Output Directory | `public` |
| System Environment Variables | включить автоматическое предоставление `VERCEL_ENV` |

Команды и output directory зафиксированы в `vercel.json`.
`api/notify-order.js` остаётся Edge Function (`runtime: edge`); `type: module` задан в `package.json`.
Не задавайте устаревший `builds`, runtime `nodejs24.x` или SPA-перенаправление всех URL в HTML.
`/app` перенаправляется на `/app/`, `/app/` переписывается в `/app/index.html`; пути ресурсов абсолютные.
Домен должен обслуживаться через HTTPS. Прокси перед Vercel отдельно не настраивался; лимит IP рассчитывается по заголовку Vercel `x-forwarded-for`.

## Переменные окружения

| Имя | Production | Preview / Development |
| --- | --- | --- |
| `ORDER_MODE` | `disabled` до завершения подготовки, затем `live` | `disabled` по умолчанию; `mock` только для согласованной проверки |
| `ORDER_ALLOWED_ORIGINS` | точные origins реально подключённых доменов, например `https://saen.uz`; несколько через запятую | точный URL конкретного preview; без `*` |
| `ORDER_HASH_SECRET` | случайный секрет минимум 32 символа | отдельный секрет |
| `UPSTASH_REDIS_REST_URL` | HTTPS REST URL базы заказов | отдельная тестовая база |
| `UPSTASH_REDIS_REST_TOKEN` | токен REST с правами GET/SET/EVAL/INCR/EXPIRE/ZADD/ZREM/ZRANGE/ZCARD | токен тестовой базы |
| `TELEGRAM_BOT_TOKEN` | секрет токена бота | не предоставлять production token |
| `TELEGRAM_CHAT_ID` | числовой ID нужного чата (возможен `-` для группы) | не требуется для `mock` |
| `VERCEL_ENV` | автоматически `production`; вручную не подменять | автоматически `preview` или `development` |

`live` вне Production и `mock` в Production запрещены сервером.
Неизвестный/отсутствующий режим, неполная конфигурация или недоступный Redis возвращают 503; заказ остаётся в очереди браузера.
Изменения env применяются к **новому deployment**, поэтому после настройки нужен redeploy.
Переменные не должны иметь `NEXT_PUBLIC_`/`VITE_` и не должны попадать в код, GitHub или скриншоты.
Секрет можно получить локально: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.

## Redis — обязательное серверное хранилище

Создать/подключить Upstash Redis через Vercel Marketplace или напрямую. REST-клиент использует HTTPS и EVAL без дополнительных runtime-зависимостей.
Включить доступные на выбранном плане резервные копии и политику **no eviction**, обеспечить запас памяти/квоты. Нельзя использовать кеш с автоматическим вытеснением для журнала заказов.
Если выбранный план не позволяет обеспечить сохранность записей и резервирование — это блокер запуска; выбрать подходящее хранилище/план.
Владелец должен проверить применимость места хранения персональных данных для своего бизнеса до добавления реальных клиентов.

Ключи: `saen:{orders}:live:order:<UUID>` содержат канонический заказ, отпечаток запроса, время приёма и статус Telegram.
У заказов **нет TTL**: автоматическое удаление записи позволило бы старой офлайн-очереди создать дубликат.
Для хранения персональных данных определить срок; при очистке оставлять идемпотентный tombstone с `fingerprint`, `order.id`, `order.total`, `mode`, `notification`, без контактов/товаров. Не удалять ключ целиком, пока возможно воспроизведение запроса старым клиентом.
Пространства `live` и `mock` разделены кодом; отдельные базы Production и Preview всё равно обязательны для изоляции доступа.

Ограничения: 60 запросов/минуту/IP (включая повторы), 10 новых заказов/час/IP, 3 новых заказа/час/телефон, 100 новых заказов/час суммарно.
Окна начинаются с первого запроса; изменения лимитов — в Lua `lib/order-store.js` с повторной проверкой тестов.
IP и телефон в ключах представлены HMAC, контакты хранятся только внутри записи заказа.
Проверка origin и эти лимиты снижают злоупотребления, но не подтверждают личность покупателя. Согласуйте лимиты с ожидаемым трафиком; распределённые боты требуют дополнительных правил Vercel Firewall/проверки человека.

## Сверка уведомлений

До включения `live` назначить ответственного за журнал и очередь сверки.
`saen:{orders}:live:review` — sorted set всех заказов с незавершённым или неуспешным уведомлением.
Запись добавляется **атомарно вместе с заказом**, удаляется только после сохранённого подтверждения Telegram.
Она сохраняется также при завершении функции между сохранением заказа и отправкой.

`ORDER_MODE=live npm run orders:review` с Redis env выполняет только чтение и выводит ID/время/статус без контактов.
При количестве больше 100 использовать `ZRANGE` с пагинацией в защищённой консоли Redis.
Проверять эту очередь при работе магазина; `sending` старше минуты и `needs_review` требуют сверки.
В логах Vercel искать `ORDER_NOTIFICATION_REVIEW` и `ORDER_NOTIFICATION_STATE_UNCERTAIN`; полные ошибки upstream, токены и контакты не логируются.
Не полагаться только на логи: при аварийном завершении запись останется в Redis без лога.

1. Найти ID заказа в Telegram и запись в защищённой консоли Redis.
2. Если сообщение есть, отметить `notification.status=sent` и известный `messageId`; убрать ID из `review`.
3. Если результата нет/он неясен, проверить у менеджера и связаться с клиентом по сохранённым контактам. Клиента не просить оформлять новый заказ.
4. Отправка повторного уведомления — осознанное ручное действие после сверки, поскольку Telegram не гарантирует exactly-once. В этой работе такие отправки не выполнялись.

## План выпуска

1. Проверить зелёный CI PR, актуальность каталога и даты запуска; все цены перенесены из исходника без коммерческого подтверждения.
2. Настроить отдельный Preview в `mock` с тестовой базой, без Telegram secrets. Тестовые записи должны оставаться только в тестовой базе; реальные уведомления не отправлять.
3. Проверить PWA на физическом iPhone: установка, первая загрузка online, авиарежим, reload, восстановление сети, сохранение черновика. Playwright WebKit не заменяет физическую проверку iOS.
4. Подготовить Production env, хранилище/backup и ответственного за очередь; оставить `ORDER_MODE=disabled`.
5. Согласовать выпуск, слить PR, получить новый deployment. Проверить GET `/app` → `/app/`, manifest, SW и статические ресурсы. GET API должен вернуть 405 без отправки.
6. После проверки условий включить `ORDER_MODE=live` и выполнить redeploy. Реальный контрольный заказ/уведомление требует отдельного разрешения владельца.

Обновление PWA: увеличить `VERSION` в `app/sw.js` при изменении любого precache-файла.
Новая версия ждёт подтверждения обновления; HTML и JS кешируются одним выпуском.
Клиент со старой версией до обновления увидит отказ старой схеме; старые четырёхзначные заказы не переотправляются новой версией автоматически.
Перед запуском сверить исторические заказы вручную. Не удалять `saen-orders` в браузерах для «исправления» очереди.

Откат: переключить `ORDER_MODE=disabled`, redeploy текущей безопасной версии. Очереди браузеров остаются сохранены.
Не возвращать старый незащищённый endpoint и не очищать Redis ради отката.

Источники конфигурации: [Vercel Edge runtime](https://vercel.com/docs/functions/runtimes/edge), [Request headers](https://vercel.com/docs/headers/request-headers), [Upstash REST](https://upstash.com/docs/redis/features/restapi), [EVAL](https://upstash.com/docs/redis/sdks/ts/commands/scripts/eval), [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).
